# Write and retain useful lessons

Choose the reader and document purpose before writing. A tutorial helps someone complete a first task, a how-to supplies steps for an existing goal, a reference supports lookup and an explanation develops the reasons. Keep a procedure focused on actions and expected observations; put substantial background in a linked explanation.

Use concrete subjects and verbs, the repository's real names and conditions before the steps they control. Keep a term consistent instead of cycling synonyms. Remove repeated setup, vague attribution, inflated wording, generic conclusions and ornamental labels. Preserve meaning and evidence when tightening prose. A precise confidence limit is not filler to delete. Follow the project's language and format rather than importing upstream's punctuation preferences as universal law.

For technical teaching, explain one user journey with how and why joined together. Start with the part the reader asked about and use a diagram or captured image only when it clarifies the mechanism. Do not turn an explanation request into implementation. For a status update, lead with user-visible progress and name each decision that actually needs the user; supply enough context to decide it without rereading the conversation.

For PRs and commits, use the repository's template and lifecycle through `pr-create`. Explain the concrete problem, resulting behavior, material tradeoff and actual verification. Link detailed runs instead of pasting a laboratory notebook. Do not replace the repository's title format with pstack's Conventional Commits format.

## Capture a preference or repeated correction

Separate an explicit owner preference, a one-off incident and a recurring mistake class. Read the nearest harness-gap ledger and relevant evidence before counting occurrences. For repeated mistakes, try the highest effective structural fix: eliminate competing owners or hand-synchronized data, express a type or schema invariant, use an existing lint or validation boundary, then add a meaningful regression. Prove a guard fails on a real prior mistake. Judgment that cannot be encoded can justify a concise instruction.

Use the existing retro and harness-change procedure. Keep fixes separate from unrelated feature work. A prose change that merely repeats a rule already ignored is not a structural remedy. Record first observations without inventing a second occurrence, and do not modify a shared skill or tracker beyond the task's authorization.

For a requested personal working-style skill, find and update an existing user-owned skill before creating another. Mine only the authorized workspace and time range, preserve uncontradicted preferences and distinguish direct requests from inferred habits. Trigger on the requested style, not every coding task. Keep it outside managed plugin caches, validate its frontmatter and references, and exercise any objective procedure. A preference draft is not evidence of improved task quality.
