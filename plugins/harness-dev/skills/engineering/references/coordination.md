# Coordinate phased and delegated work

Use this procedure when the task needs multiple verifiable units or an authorized delegation. Follow the session's delegation policy. A broad implementation request alone does not override a restriction on spawning agents, and this reference does not require fan-out.

## Plan at the scale of the task

Name the completion predicate, dependencies, owned paths and verification for each unit. Resolve the riskiest empirical unknown with a small probe before a wide migration. One or two obvious edits do not need a program store. For larger work, keep a dependency table and a [decision trail](work-sessions.md#keep-a-decision-trail). A planning-only request ends with that deliverable; an already authorized implementation continues.

Distinguish one task driven to completion, one bespoke multi-phase run, and a standing multi-day program. Scale the record accordingly. For a program, keep units, current revisions, verdicts, blockers and owner assignments in files with one writer each. Derive the status report from those records. Prove one representative unit end to end before scaling an unfamiliar recipe.

## Give each writer an owned boundary

A useful brief names the goal, allowed and forbidden paths, upstream context, acceptance checks, exact verification, time or effort limit, current instructions and the expected report. A dependent unit needs its predecessor's output, not merely its position in a queue. Use separate worktrees or output paths for independent writers. Separate mutable files or keys before adding locks; a shared JSON file with different fields still has multiple writers.

Coverage workers get disjoint slices. Competing-design workers get the same task, isolated outputs and the same evidence. Define selection criteria before seeing their results. Read every candidate; choose one coherent base and integrate useful ideas deliberately. A judge cannot assess an output that is still being written. If authorized reviewers are unavailable, perform a sequential comparison and state that it was not an independent panel.

Use only model settings the runtime exposes and the user or applicable policy permits. Preserve existing choices. Record actual identity when known; an inherited model, rejected slug or unknown identity does not establish diversity. A setup request can produce a proposed role table, but do not invent entitlements or silently install a global model rule.

## Supervise the work that exists

Track each unit's terminal result and evidence at the named revision. A completion is a queue event; finish the current critical state update before integrating it. Read outputs and verify receipts, then refill only the work the coordinator can review. Count missing or abandoned slices as gaps. A stale or late result must be reconciled with current code before acceptance.

Probe actual progress without waking idle workers merely to ask for status. On failure, classify the cause, bound retries and adjust the scope or environment. A repeated identical failure needs investigation rather than another identical retry. Keep the original completion predicate; report a real impasse instead of inventing success. Do not create a recurring watcher or schedule unless that persistent operation was requested.

One owner changes a PR stack's topology. Independent PRs can proceed independently; coupled PRs follow a declared base chain. [PR operations](pr-operations.md) owns the checks and authorized landing. An operator stop reaches all active work, preserves its files and records the next resume point.

## Runtime-specific capabilities

Discover available adapters before promising Cursor loops, cloud agents, model panels or automation triggers. For a requested webhook UI, require a real configured trigger and secure server-side secret delivery. Treat payloads as data, keep credentials out of the browser and prove a harmless event before claiming the connection works. Do not install a network service, expose a listener or create automation merely because upstream has instructions for it. Missing runtime capabilities remain explicit gaps; the portable investigation, ownership and verification steps can still proceed.
