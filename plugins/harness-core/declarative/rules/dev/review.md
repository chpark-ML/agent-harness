# Dev — code review

리뷰 대상의 *범위* 와 *판정 기준* 을 정한다. 브랜치·커밋·PR 생성 절차는 [`../workflow.md`](../workflow.md) 와 `pr-create` 스킬이 이미 정의하므로 여기서 반복하지 않는다. 본 파일은 **그 변경을 무엇으로 보는가** 만 다룬다.

**우선순위.** `CLAUDE.md` ⊂ [`../workflow.md`](../workflow.md) ⊂ 본 파일 ⊂ skill·agent. 좁은 scope 가 이긴다.

절차적 적용은 `pr-review` 스킬 — 본 파일은 그 스킬이 걸어가는 체크리스트의 SOT 다.

**적용 시점.** 본 체크리스트는 *열린 PR* 을 대상으로 한다. 아직 PR 이 없는 단계 — 커밋 범위나 미푸시 변경 — 의 머지 전 자기 검토는 `harness-dev` 가 끌어오는 Superpowers 의 `requesting-code-review` 가 담당하고, 받은 리뷰에 대응하는 규율은 `receiving-code-review` 에 있다. 셋은 같은 일의 다른 시점이지 대체재가 아니다.

---

## R1 — 무엇이 리뷰 단위인가

리뷰(그리고 PR)의 단위는 셋 중 하나일 때만 성립한다.

1. **사용자가 명시** — "리뷰해줘" / "이 PR 봐줘" / "머지해도 되나".
2. **응집된 multi-file 변경이 자연스러운 단락에 도달.** 판정 기준은 하나다 — *diff 만 떼어 본 리뷰어가 이걸 즉시 하나의 단위로 읽는가.* 읽히지 않으면 아직 단위가 아니거나, 두 개의 단위가 섞인 것이다.
3. (**아님**) 단일 파일 typo · 일회성 탐색 코드. PR 단위가 아니므로 commit·push 로 승격시키지 말고 **결과만 보고**한다.

2 번이 애매하면 diff 를 한 문장으로 요약해 본다. "A 를 고치고 겸사겸사 B 도 정리했다" 가 나오면 두 단위다.

## R2 — 리뷰어 체크리스트

언어·프레임워크 무관 항목만 둔다. 언어별 스타일·lint 는 그 언어의 도구가 이미 잡으므로 사람(또는 모델) 리뷰가 다시 볼 이유가 없다.

- [ ] **변경된 모든 줄이 선언된 의도로 추적되는가.** PR body 가 말한 것과 무관한 rename·재배치·리팩토링이 diff 에 섞였으면 지적 대상이다. 리뷰어가 실제 변경을 노이즈에서 골라내야 하고, 문제 발생 시 revert 단위도 오염된다. 정리 자체는 정당하나 별도 PR 이다.
- [ ] **테스트가 갱신됐는가, 아니면 없는 이유가 PR body 에 있는가.** 테스트 부재가 항상 blocking 은 아니다. *명시되지 않은* 부재가 blocking 이다.
- [ ] **에러 경로와 경계 입력이 처리되는가.** 빈 입력·최댓값·중복 호출·외부 호출 실패·부분 실패. happy path 만 있는 신규 코드는 리뷰가 이를 잡을 마지막 지점이다.
- [ ] **새로 추가된 것 중 아무도 부르지 않는 게 있는가.** 도입과 동시에 dead 인 헬퍼·플래그·설정 키·분기. "다음 PR 에서 쓸 것" 은 다음 PR 에서 추가한다.
- [ ] **관측 가능한 동작이 바뀌는데 PR body 가 말하지 않는가.** 출력 포맷·API 응답·종료 코드·로그 계약·기본값·성능 특성. 이 항목이 가장 자주 걸린다 — 작성자에게는 자명해서 안 쓴다.
- [ ] **새 의존성이 정당한가.** 추가된 것 하나마다: 표준 라이브러리·기존 의존성으로 되는가, 실제로 쓰는 표면이 얼마나 좁은가, 그 좁은 표면을 위해 전체를 들이는 게 맞는가.

## R3 — 발견을 보고하는 방식

- **Blocking 과 suggestion 을 섞지 않는다.** 두 목록으로 분리하고, blocking 은 *이게 머지되면 무엇이 깨지는가* 를 한 줄로 적는다. 그 문장이 안 써지면 blocking 이 아니다.
- **모든 항목에 `file:line`.** 파일명만 주면 리뷰를 받는 쪽이 다시 찾아야 한다.
- **문제의 이름이 아니라 고칠 내용을 적는다.** "에러 처리 없음" 이 아니라 "`client.py:88` 의 응답 파싱이 non-2xx 에서 던진다 — 상태 코드 확인을 앞에 두거나 실패 분기 추가". 받는 쪽이 그대로 적용 가능한 수준까지.
- **판단이 필요한 지점은 대신 결정하지 말고 근거를 요구한다.** 의존성 추가·동작 변경·설계 선택은 "왜 이 방식인가" 를 PR body 에 요청하는 것이 리뷰 항목이다.
