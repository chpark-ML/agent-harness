# harness gaps — 원장

`CLAUDE.md` §5 의 "두 번 이상 발생하면 제안한다" 를 세기 위한 파일이다. 세션을
넘겨 발생을 세는 장치가 이것뿐이므로, **1회차도 적는다** — 1회차를 안 적으면
2회차가 영원히 1회차로 보인다.

한 항목: 날짜 · 파일:줄 · 무슨 일이 있었나 · 몇 회차인가. 2회차가 되면 그때
PR 본문 `## Notes` 로 올라가고, 고치는 것은 그다음이다.

---

## 2026-08-07 — `superpowers:finishing-a-development-branch` 가 위임을 받지 않는다

- **어디**: `docs/adr/0009-external-dependencies.md` — 갱신 절의 위임 판정
- **무슨 일**: ADR-0009 는 머지·브랜치 정리를 Superpowers 쪽에 남기고 우리는
  PR 생성까지만 한다고 정했다. 실측에서 "이 PR 머지하고 브랜치 정리해줘. squash
  로 넣고 원격 브랜치도 지워줘" 가 **세 번 다 `Bash` 로** 갔다. 위임한 상대가
  그 자리를 받지 않는다. 사용자는 규약 없는 맨 `git` 명령을 받게 된다.
- **왜 지금 안 고치나**: 1회차다. 그리고 고치는 방법이 둘인데 어느 쪽인지
  모른다 — 우리가 `pr-finish` 를 만들어 자리를 메우거나, 위임 자체를 철회하고
  `pr-create` 의 범위를 넓히거나. 둘 다 되돌리기 비싼 결정이라 두 번째 발생을
  기다린다.
- **회차**: 1

## 2026-08-07 — 스킬 본문의 경로 오타는 조용히 죽는다

- **어디**: `plugins/harness-core/skills/pr-create/SKILL.md:90`
- **무슨 일**: Step 6 을 쓰면서 `.claude/harness-gaps.md` 를 `.claece/...` 로
  적었다. `[ -f ... ] && ...` 형태라 파일이 없으면 조용히 아무 일도 안 하고
  넘어간다 — 즉 **이 절이 영원히 안 도는데 아무도 모른다.** 같은 회 안에서
  발견해 고쳤다.
- **일반화**: 훅은 `verify-*.sh` 가 지키고 프론트매터는 `verify-frontmatter.sh`
  가 지키는데, **스킬 본문 안의 경로·명령은 아무도 안 본다.** `check-claims.sh`
  가 덱의 수치를 검사하듯, 스킬이 언급하는 경로가 실재하는지 훑는 검사가 같은
  종류의 빈틈을 덮는다.
- **왜 지금 안 고치나**: 1회차. 다만 이건 값이 싼 검사라 2회차가 나오면 바로
  만든다.
- **회차**: 1

## 2026-08-07 — R1-3 예외 조항이 "커밋 보류" 를 말하는데 커밋된다

- **어디**: `plugins/harness-core/declarative/rules/core/workflow.md:20` (R1-3)
- **무슨 일**: 규칙은 *"단일 파일 typo · 한 줄 수정 · 임시 탐색은 PR 단위가
  아니다. 결과만 보고하고 commit·push 는 보류"* 라고 적혀 있다. 한 줄 수정
  과제를 준 벤치마크 3회에서 에이전트는 **브랜치는 안 팠지만(예외 준수) 커밋은
  했다(예외 위반)**. 예외의 앞 절반만 지켜진 셈이다.
- **왜 그럴 수 있나**: 같은 절의 불변량이 "`main` 직접 **push** 금지" 로 두 번
  다 *push* 를 말한다. commit 만 하는 요청에는 걸리지 않는 문구다.
- **왜 지금 안 고치나**: 1회차이고, 관측 조건이 "커밋해줘" 라고 명시적으로
  지시한 경우였다 — 사용자 지시가 규칙의 보류 권고를 이긴 것이라면 정상 동작에
  가깝다. 지시 없이도 커밋하는 사례가 나오면 2회차로 센다.
- **회차**: 1

## 2026-08-07 — `ask` 티어가 헤드리스에서 PR 플로우를 도달 불가로 만든다

- **어디**: `plugins/harness-core/declarative/settings-fragment.json` — `permissions.ask` 의 `Bash(git push:*)`
- **무슨 일**: 비대화형 `claude -p` 세션은 권한 프롬프트에 답할 수 없어 push 가
  항상 거부된다. `acceptEdits` · `dontAsk` · `bypassPermissions` 세 모드 모두에서
  재현했다. `pr-create` 스킬은 Step 5 가 push 라서 헤드리스에서는 **완주가
  구조적으로 불가능**하다.
- **왜 지금 안 고치나**: 1회차이고, `ask` 티어 자체는 의도된 설계다 (되돌리기
  어려운 동작은 사람이 승인한다). 답이 자명하지 않다 — 헤드리스를 감지해
  완화할지, `pr-create` 가 push 직전에 멈추고 명령을 내어줄지, 아니면 문서로만
  알릴지. 2회차가 나오면 셋 중 하나를 고른다.
- **회차**: 1

## 2026-08-07 — `--with` 를 반복하면 앞엣것이 조용히 사라졌다

- **어디**: `plugins/harness-core/bin/harnessctl:54` (인자 파싱)
- **무슨 일**: 사용법은 `--with dev,research` 인데, `--with dev --with research`
  라고 쓰면 뒤엣것이 앞엣것을 덮어써서 **사용자가 명시적으로 요청한 모듈이 경고
  없이 빠졌다.** 문서 정리 중 실제로 이 형태로 쳤다가 발견했다.
- **1회차인데 왜 바로 고쳤나**: 이건 후보 기능이 아니라 **조용한 오동작** 이다.
  §7 의 "두 번 발생을 기다린다" 는 새 규칙·새 훅을 늘릴 때의 기준이지, 이미
  배포된 코드가 요청을 말없이 무시하는 경우에 적용할 기준이 아니다. 반복 시
  누적하도록 고치고 `verify-install.sh` 에 회귀 케이스 둘을 박았다 (90 → 92).
- **회차**: 1 (해결됨)

## 2026-08-07 — 시크릿 픽스처가 GitHub push protection 에 걸린다

- **어디**: `evals/incidents.sh` · `plugins/harness-core/scripts/verify-secret-scrubber.sh`
- **무슨 일**: 저장소를 public 으로 올리는 첫 푸시가 거부됐다. GitHub 이 우리
  Slack 토큰 **픽스처** 를 진짜 시크릿으로 판정했다. 시크릿 탐지기를 시험하려면
  시크릿처럼 생긴 문자열이 있어야 하는데, 그게 정확히 스캐너가 찾는 것이다.
- **고친 방법**: 우리 정규식(`xox[abprs]-` + 20자)에는 걸리고 GitHub 의 구조
  판정에는 안 걸리는 값으로 교체. 훅 차단(exit 2)과 벤치마크 27/29 는 그대로다.
- **일반화**: 새 시크릿 패턴을 추가할 때마다 픽스처가 실제 스캐너에 걸리는지
  확인해야 한다. private 일 때는 드러나지 않는 종류의 문제다.
- **회차**: 1 (해결됨)

## 2026-08-07 — 플러그인 `bin/` 은 사용자 셸에서 안 보인다

- **어디**: `install.sh` · `README.md` (설치 안내)
- **무슨 일**: 사용자가 터미널(zsh)에서 `harnessctl` 을 쳤는데 없었다. 플러그인
  `bin/` 은 Claude Code **Bash 도구** 의 PATH 에만 올라간다. README 는 그냥
  "PATH 에 자동으로 오른다" 고만 적어 두어 사용자가 터미널에서 칠 수 있는 것처럼
  읽혔다 — 설치가 깨진 것처럼 보인다.
- **왜 심링크로 못 푸나**: 캐시가 버전별 디렉터리(`harness-core/1.6.0/bin/`)라
  업데이트마다 경로가 바뀐다. 지금 거는 심링크는 다음 업데이트에 죽는다.
- **고친 방법**: `~/.local/bin/harnessctl` 에 실행 시점 해석 shim. 평범한
  실행 파일이라 셸 무관하고, `sort -V` 로 최신 버전을 고르므로 업데이트를 따라간다.
  PATH 에 없으면 `$SHELL` 을 보고 맞는 rc 파일과 한 줄을 안내한다.
- **1회차인데 왜 바로 고쳤나**: 사용자가 첫 명령에서 막혔다. 설치기가 "완료" 라고
  말한 뒤 안내한 명령이 동작하지 않는 것은 후보 기능이 아니라 결함이다.
- **회차**: 1 (해결됨)
